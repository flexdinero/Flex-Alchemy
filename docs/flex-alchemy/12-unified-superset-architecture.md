## 1. Mission, the core gap, and the meaning of "one-shot"

**Flex Alchemy** is an autonomous technology development, verification, and operations platform that turns a visionary's high-level mission into a continuously improving, production-hardened technology product by coordinating specialized AI capabilities, deterministic development tools, living technical intelligence, independent adversarial verification, and human direction. (Source B mission statement; Source A's framing — "the founder directs outcomes; Alchemy manages the technical work and presents evidence" — is the same mission stated operationally.)

### 1.1 The core gap (Source B, retained in full)
Today, an everyday founder or visionary can tell an AI, *"Build my platform,"* and receive a polished-looking user interface or thousands of lines of raw code. However, without deep, master-level expertise across the full spectrum of software engineering, that person cannot easily tell:
* Whether the underlying system architecture is sound or brittle.
* Whether third-party integrations and APIs actually work in production or are just mocked on screen.
* Whether customer data, credentials, and financial flows are properly isolated and protected.
* Whether the application can handle real concurrent users, edge cases, network failures, and scale.
* Whether half of the requested business logic was quietly skipped or stubbed out behind a button.

Flex Alchemy takes full operational responsibility for managing the entire path from initial idea to a verified, operating product:
* **The Human Visionary** supplies the mission, domain vision, priorities, and high-level business decisions that only a human founder can make.
* **Flex Alchemy** supplies the full-spectrum engineering organization, technical intelligence, architectural discipline, execution tooling, adversarial testing, security auditing, and verifiable proof needed to bring that vision to life.

### 1.2 The practical meaning of "one-shot" (Source B) layered with the honest quality contract (Source A)
> **A user gives the system one high-level mission, while Flex Alchemy autonomously performs hundreds of carefully managed, verified steps behind the scenes across research, planning, multi-session execution, testing, repair, and review.**

Grounded engineering truth behind the claim:
* **Environment & Feedback Loops Drive Speed:** In OpenAI's internal engineering experiments where agents built a production system in roughly one-tenth the time of manual coding, that 10x compression depended on experienced engineers designing rigorous environments, harnesses, and automated feedback loops around the models. Flex Alchemy bakes that exact harness and feedback architecture into the platform itself so non-technical founders get principal-level engineering discipline out of the box.
* **Long-Horizon Task Persistence:** As benchmarks like METR and Anthropic's research on long-running agents demonstrate, AI reliability drops sharply over long durations unless work is broken into verified checkpoints with durable state artifacts stored outside the model's temporary context window.
* **Speed Without Defect Multiplication:** A system that merely generates code faster without independent verification simply generates defects and technical debt faster.

**Source A's quality contract governs all claims made under this definition:**
- Every requested outcome is recorded, clarified where necessary, and mapped to observable acceptance conditions.
- Every completion claim identifies the artifact, environment, version, and supporting evidence.
- Critical uncertainty, unsupported domains, missing access, and failed checks remain visible.
- The system can stop, recover, and seek appropriately qualified review without disguising incomplete work.
- Improvements preserve prior verified behavior unless the user authorizes a change.
- The user owns or can export the code, project memory, documentation, data, and decision history subject to provider contracts.
- There is no achievable universal guarantee of zero flaws or no limitations. Confidence must be scoped to what was tested, for whom, under which conditions, and how recently. Formal verification can strengthen selected properties under explicit assumptions; it cannot prove an unspecified product universally perfect.

**Domain capability-envelope rule (Source A, layered over Source B's ambition):** support new products and existing codebases — web and mobile applications, APIs, integrations, automations, AI systems, developer tools, data platforms, enterprise workflows, and eventually specialized scientific or embedded systems. **Each domain has a separately proven capability envelope. Web-app competence does not certify trading execution, medical systems, robotics, or hardware safety.**

### 1.3 Six Non-Negotiable Operating Aims (Source B)
1. **Fast when the work is well understood** (by mounting pre-verified, reusable architectural foundations rather than reinventing boilerplate).
2. **Ruthlessly honest when something is unverified** (strictly distinguishing between "UI exists" and "connected, tested, and verified with evidence").
3. **Persistent when a project spans many sessions** (maintaining a durable 5-Pillar Project Brain and AST symbol graph outside the context window).
4. **Able to detect and repair its own mistakes** (catching compilation, logic, visual, security, and runtime failures through deterministic gates and self-healing loops).
5. **Able to involve a person or specialist at the exact right time** (escalating clear business trade-offs or blocked external credentials rather than guessing silently).
6. **Continuously better because it learns from actual outcomes** (`Build → Verify → Release → Observe → Learn → Improve both the product and Flex Alchemy itself`).

## 3. Vision Translator (alias: Intent Translator & Socratic Spec Compiler)

A regular person states a high-level goal in plain English. Flex Alchemy automatically recognizes that a brief statement implies dozens of critical questions the user might not know to ask:
* Who are the different user types, roles, and organizational tenants?
* What exact actions does each user need to perform from start to finish?
* Where does the underlying data originate (user input, webhooks, third-party APIs, legacy portals, market feeds)?
* Are external firms or providers offering documented APIs, or only web portals / emails?
* How will authentication, workspace isolation, and role-based access control work?
* How are sensitive records (PII, financial credentials, proprietary algorithms, claim files) encrypted and protected?
* What happens when an external integration, API, or network connection fails or times out?
* What can be built and verified immediately in development versus what is blocked waiting on outside credentials or legal approval?
* How will the business measure whether the product is actually succeeding in production?

**Operating Rule:** extract answers from the founder's existing materials first, synthesize sensible architectural defaults, and ask **only** the high-leverage questions that materially affect the outcome. (Source A adds: ask only when the choice affects intent, spending, access, risk, or irreversible consequences; resolve routine technical choices autonomously within the mission; continue independent authorized work while waiting.)

### 3.1 All 9 input streams (Source B) ∪ Source A intake rules
1. **Plain-language conversation and voice notes** (spoken or typed natural language).
2. **Existing websites and live application links** (for inspection, cloning, or integration).
3. **GitHub repositories and existing codebases** (full AST and dependency ingestion).
4. **Documents, PDFs, spreadsheets, and architectural diagrams** (business plans, SOPs, data samples).
5. **Screenshots, interface examples, and screen recordings** (visual inspiration, competitor flows, bug recordings).
6. **Competitor products** (feature parity analysis and differentiation mapping).
7. **Existing customer research, transcripts, and sales calls** (extracting real user pain points and terminology).
8. **API documentation and integration credentials** (OpenAPI specs, webhook docs, sandbox keys).
9. **Previous AI conversations and project plans** (inheriting full historical context without repetition).

Source A intake layering: preserve the original source; distinguish user requirements from assistant suggestions; detect contradictions explicitly — prefer a clear newer user decision over an older proposal, never infer precedence merely from file modification time; maintain change requests showing schedule, cost, architecture, and verification impact; capture data rights for every input.

* **Adaptive Socratic Questioning**: only high-leverage trade-off questions in plain language around cost, speed, privacy, and user experience — after first exhausting all answers available in uploaded files, repositories, URLs, and prior chats.

## 4. Development Director (alias: Meta-Orchestrator & DAG State Governor)

The core autonomous management brain — coordinating AI work the way a world-class VP of Engineering, Principal Technical Program Manager, and Delivery Lead would (Source B); implemented as a **durable** director with deterministic execution semantics (Source A).

### 4.A Break the mission into manageable, risk-ordered work (Source B)
Live Directed Acyclic Graph (DAG) and dependency map answering: what architectural contracts and schemas must be decided first; which modules and vertical slices can be built safely in parallel; which tasks depend on external API credentials, vendor approval, or human sign-off; what foundational proofs must pass before downstream work continues; which parts carry the highest technical or economic uncertainty. *Rule: never spend days polishing a UI dashboard before proving the underlying API, payment provider, broker connection, or intelligence model actually supports the business model.*

### 4.B Maintain a live, durable project state outside the context window (union)
The Director tracks at every moment (Source B's nine): 1. What is requested 2. What has been implemented (exact commits, files, endpoints) 3. What has been independently tested 4. What failed (exact error logs, stack traces, falsified assumptions) 5. What has changed 6. What is blocked (and the exact external key or human decision needed) 7. What remains uncertain 8. What work comes next 9. What it has spent (real-time token, compute, and third-party API costs vs. budget ceilings).

Source A execution-semantics layering (mandatory underneath): durable checkpoints, worker leases, heartbeats, cancellation tokens, retry ceilings, backoff, dead-letter handling, and **fenced writes**. At-least-once delivery requires idempotent effects or reconciliation. A crash after an external action but before its receipt is recorded must trigger an outcome query before retrying. **Never blindly repeat a payment, message, deployment, or data mutation.** A task is not complete because an agent emitted a completion message; the Director evaluates the evidence contract; the model does not directly edit the global completion ledger. Prefer deterministic code for known operations and agents for open-ended reasoning; use one agent by default and add specialists only when isolated work or independent review creates measurable value.

Work-state machine (Source A): requested → specified → planned → executing → implemented → verifying → verified → released → monitored; also blocked, rejected, failed, cancelled, superseded, rolled-back. A verified record becomes stale when relevant code, data contract, policy, or environment changes. (Founder-facing labels in §10.3 map onto these states.)

### 4.C Choose the right level of oversight dynamically (union)
* **Low-Risk / Well-Understood Task:** 1 capable Specialist Worker + deterministic automated compiler/linter/unit checks.
* **High-Risk / Complex / Security-Critical Task** (multi-tenant permissions, autonomous trading execution, billing, production data migrations): 1. Dedicated Planning & Architecture Role 2. Specialist Building Role 3. Independent Code & Contract Reviewer 4. Dedicated Security & Privacy Reviewer 5. Automated End-to-End, Property-Based & Mutation Tests 6. Human Specialist or Founder Approval Gate (when required by policy). (Source B's prompt formulation adds a Formal Specification Role between Planning and Building; both sequences are retained — Formal Specification applies where §10.4 formal verification is in scope.)
* The Director scales oversight based on task risk and **measures whether added review improves verified outcomes enough to justify its cost and latency** (both sources agree; Source A: optimize coordination cost, not agent count).

### 4.D Detect and break unproductive loops — the 3-Strike Loop Breaker (union)
After a strict threshold (3 failed attempts), the Director automatically: 1. **Records the failure** and freezes the repetitive retry loop. 2. **Diagnoses and classifies the root cause**: unclear or contradictory requirements / missing external access, credentials, or rate limits / flawed architecture or broken interface contract / development environment or sandbox failure / underlying model capability limitation. 3. **Changes the engineering approach** (e.g., simplifying the pattern or isolating the failing component). 4. **Brings in a different tool, higher-reasoning model, or independent reviewer** if justified. 5. **Escalates to the Founder Command Center** with a concise, plain-language explanation and actionable options if human intervention is required. (Source A adds runaway-loop detection signals: repeated tool calls, unchanged artifacts, recurring errors, and no new evidence.)

### 4.E Preserve immutable accountability — Architecture Decision Records (union)
Every significant decision is logged permanently with six mandatory fields (Source B): 1. What was decided 2. Why it was chosen 3. What alternatives were considered 4. What empirical evidence or benchmark supported the choice 5. What trade-offs remain 6. What specific future trigger or scale threshold would cause the decision to be revisited. (Source A adds: owner and date on every final ADR; the initial ADR set ADR-001…010 is preserved in §16.)

## 11. Dynamic Model & Agent Selection, Model Strategy & the Proprietary Model Foundry

### 11.1 Task profiles (Source B §11)
Flex Alchemy is never locked to a single AI model or vendor. Tasks require distinct profiles: deep architectural reasoning and subtle bug diagnosis; high-speed multi-file syntactic code refactoring; massive-context repository and document synthesis (1M+ tokens); multimodal visual UI/UX critique and pixel-level layout inspection; live browser interaction and DOM navigation; adversarial security threat modeling and exploit generation; live web and technical documentation research; low-latency, low-cost classification and routing; speech, audio, video, and avatar synthesis/understanding.

### 11.2 The 8-Step Empirical Model Routing Loop (Source B) ∪ Source A routing economics
For every subtask in the DAG: 1. Identify the exact task type and required verification gate. 2. Determine the required privacy, data-residency, and security tier. 3. Check live model capabilities, context limits, and provider availability. 4. Estimate total token/compute cost and expected latency. 5. Select and dispatch the optimal candidate model(s). 6. Evaluate the actual output against deterministic compiler/test gates. 7. Escalate or switch models immediately if the output fails verification (without repeating the same prompt in a loop). 8. Record empirical outcome telemetry (pass rate, retries, cost, duration) to continuously update routing weights. *(For high-impact architectural or security decisions, independent multi-model cross-examination may run — agreement between two models is never proof of truth without deterministic verification.)*

Source A economics layering: minimize **total cost per accepted outcome**, including retries, infrastructure, tools, and review — a cheap model with many failed attempts can be more expensive per verified result. Use capable lower-cost models for bounded extraction, metadata formatting, simple transformations, and deterministic uploads when they meet the quality bar; stronger models for ambiguous architecture, difficult debugging, synthesis, and high-impact independent review. Deterministic code is preferable when inference adds no value. Maintain exact model identifiers and configuration snapshots in run records; re-run representative evaluations after model, prompt, skill, tool, or harness changes. Privacy-aware caching and batching where valid; never reuse cached evidence across tenants or after relevant inputs change; provider fallback must preserve required capabilities and privacy constraints — a fallback is not automatically equivalent. Compare single-agent and specialist configurations experimentally; multi-model agreement is weak evidence if models share assumptions.

**Controlled evaluation criteria for adopting new frontier models (Source B):** 1. Verified success rate on private representative tasks 2. Strict adherence to negative constraints and formatting contracts 3. Factual accuracy and architectural completeness 4. Tool-use and MCP/function-calling reliability 5. Security behavior and resistance to prompt injection 6. Total end-to-end cost (including retries and context overhead) 7. Time-to-completion and token streaming speed 8. Ability to respect existing project context without introducing regressions.

### 11.3 Provider-access reality (Source C, objection 3 — kept as information only under the Founder Ruling, doc 11; not a preset, imposes no architecture)
Routing over models that cannot be called is fiction, for any AI product. The model layer therefore records, per provider: **access status, credit balance/expiry, and which Alchemy stages are blocked when a provider lapses**. Flex's access picture at merge time (information, maintained from his startup-program applications): frontier access is being pursued through startup credit programs (Microsoft/Azure OpenAI and AWS Bedrock are the open routes; Anthropic's startup cohort is closed until its next window), and across his wider router catalog only a few provider keys are actually live.

### 11.4 Should Flex train its own model? — staged progression (Source A) with the Foundry pipeline inside it (Source B)
**Yes — preserved as a serious strategic capability, begun from a specific measurable gap, not a foundation-model project intended to absorb all human expertise** (Source A). The strongest initial proprietary asset is likely the combination of verified task histories, failure diagnoses, task-specific skills, acceptance tests, and outcome labels (strategic inference, labeled as such).

Source A progression (advance only when the gate is met): **A: Baseline** (existing frontier/open models with good tools, retrieval, skills — representative tasks and failure categories measured) → **B: Data advantage** (curate authorized traces, artifacts, labels, difficult counterexamples — provenance, quality, consent, and train/eval separation established) → **C: Narrow specialist** (train a router, evaluator assistant, or repeated bounded engineering behavior — training plausibly addresses the identified failure or cost) → **D: Adapt an existing model** (SFT/LoRA or other suitable post-training on licensed weights — candidate improves held-out outcomes without material regressions) → **E: Preference/reward optimization** (reliable preference labels or executable rewards — reward validity and hacking resistance demonstrated) → **F: Distillation and serving** (teacher terms permit use and total serving economics improve) → **G: Continued pretraining or foundation research** (only with a differentiated thesis, corpus, compute, and team — a funded research case beats adaptation alternatives). Training a broadly competitive foundation model from scratch is not a prerequisite for Alchemy; no budget or training job is set from this document alone; compute is estimated from the chosen model, tokens, sequence lengths, optimizer, hardware, throughput measurements, and number of experiments — not a generic price guess. Current warning (Source A): OpenAI's documented self-serve fine-tuning availability has changed; do not assume a new account can use older tutorials — verify a currently supported route or consider suitable open-weight training infrastructure (S12, S31).

**The Proprietary Model Foundry — "Alchemy-Core" (Source B, Part III.6 — the training pipeline that executes inside stages D–G above):** sovereign specialized models **`Alchemy-Core`**, **`Alchemy-Reasoner`**, **`Alchemy-Verifier`**, **`Alchemy-Quant`**, motivated by vendor rate limits, shifting model behavior, and generic training biases in 100%-API reliance.
* **Stage 1 — Elite corpus curation:** peer-reviewed papers and technical reports from ACM, IEEE, USENIX (OSDI, SOSP, NSDI), VLDB, SIGMOD, NeurIPS, ICML, ICLR, cryptography archives (IACR), and quantitative finance journals; master-class open-source codebases that pass strict static analysis, high test coverage, memory-safety, and architectural cleanliness gates (e.g., Linux kernel subsystems, Rust compiler & standard library, PostgreSQL storage engine, SQLite, Tokio, Chromium, Kubernetes, Lean 4 `mathlib`, Dafny verified libraries); real-world engineering post-mortems & security advisories (institutional incident reports, CVE root-cause patches, NIST/OWASP security benchmarks, distributed systems failure analyses). *(Governed by §6.5 rights discipline — ingestion only with permitted use established.)*
* **Stage 2 — Synthetic Execution-Verified Trajectory Generation:** the 14-Tool Execution Harness generates multi-step trajectories (`Ambiguous User Prompt → Socratic Spec Compilation → Architecture & TLA+ State Check → Implementation → Compiler/LSP Error Diagnosis → Property & Mutation Testing → Security Audit → Verified Passing Artifact`). Only trajectories that pass 100% of the deterministic verification gates are admitted into the training dataset.
* **Stage 3 — Modern 4-Phase Training & Alignment Pipeline (CPT → SFT → RLVR/GRPO → DPO):** 1. **Continued Pre-Training (CPT)** over systems architecture, formal verification languages (`TLA+`, `Dafny`, `Lean 4`, `Rust`), quantitative mathematics, and the Flex Alchemy ontology. 2. **Supervised Fine-Tuning (SFT)** on golden multi-agent trajectories from the 14 Specialist Teams and certified Skills. 3. **Reinforcement Learning with Verifiable Rewards (RLVR) via GRPO** — replacing subjective human-preference rewards (which encourage bluffing) with objective, deterministic programmatic rewards: positive reward only when generated code compiles cleanly, passes unit/property/mutation tests, satisfies formal verifiers, passes SAST/DAST security checks, and meets latency SLAs — plus an explicit **Epistemic Integrity Reward** for accurately assigning the Honest Status Labels and refusing to claim completion when an external dependency is missing. 4. **Direct Preference Optimization (DPO) & Red-Team Hardening** against prompt injection, insecure coding shortcuts, and architectural drift.
* **Stage 4 — Modular Specialist Fleet (MoE / LoRA Adapters) & Continuous Learning Flywheel:** specialized adapters per role (`Vision Translator`, `Development Director`, `Polyglot Builder`, `Adversarial QA/Verifier`, `Autonomous CSO`) alongside frontier external models via the 8-Step Empirical Model Router.

**What to train on (Source A, doc 05 §6):** permissioned examples containing the user objective, relevant context, permitted tools, constraints, observable actions, resulting artifacts, verifier outcomes, cost, and human corrections; failed attempts with accurate failure labels and the verified repair, not merely fluent "successful" answers; hidden model reasoning is not collected as a requirement. Private client code, credentials, personal data, and commercial information are protected; cross-customer training is opt-in with explicit permitted use; default tenant isolation applies. Externally sourced material, human-produced examples, generated candidates, and independently verified synthetic tasks are provenance-separated. Research papers teach concepts; executable tasks teach application — convert selected research into reproducible experiments, implementation constraints, and evaluation cases; citation volume is not mastery.

**Data and model release gates (Source A, doc 05 §7 — all 8):** 1. Dataset lineage, permitted-use records, deduplication, quality checks, redaction. 2. Split by repository/project and time, not random near-duplicate snippets. 3. Frozen hidden test sets; evaluation materials kept out of training and skill references. 4. Comparison against the same baseline harness, tools, budgets, and environments over repeated trials. 5. Measure task success, instruction adherence, calibrated abstention, security, privacy leakage, general-capability retention, latency, and total cost. 6. Audit reward hacking (passing tests by deleting functionality, editing the grader, leaking solutions, falsifying evidence). 7. Version dataset, base model, adapter, optimizer settings, training code, and serving configuration; retain model/data cards. 8. Shadow, canary, observe, roll back on regression. (Published work shows risks from indiscriminate recursive use of generated data — S32 — not a blanket prohibition on synthetic data; independently checked synthetic tasks are used alongside reliable original data; representativeness and long-tail failures are tracked; fine-tuning/retrieval interactions and forgetting need explicit evaluation — S33.)

**Self-improvement boundary (Source A, doc 05 §8):** Alchemy may propose improvements to its prompts, skills, code, routing, and models; the production system must not silently rewrite its own authority, protected tests, evidence rules, or success criteria — an independently controlled promotion path evaluates candidate improvements. AlphaEvolve (S34) illustrates the value of verifiable objectives in bounded optimization; apply that pattern where correctness can be checked and expert judgment where it cannot. Universal autonomous self-improvement remains an unproven ambition, not a platform feature to claim at launch.

**Three kinds of learning (Source A, doc 05 §1 — the frame the Foundry sits inside):** Retrieval and structured memory (current facts, private project context, authoritative references — failure mode: wrong/stale retrieval or poisoned memory) · Skills and deterministic tools (repeated procedures and operational standards — failure mode: irrelevant trigger, brittle instructions, unsafe scripts) · Weight training (recurring behavior, specialized judgments, efficient execution — failure mode: overfitting, forgetting, contamination, poor economics). These complement each other: a model cannot retain an ever-changing ecosystem in its weights; retrieval does not automatically teach reliable execution; a skill cannot grant capabilities absent from the model and tools. **Retrieve changing knowledge; encode reusable procedures in skills; train weights only for demonstrated behavior or cost gaps.**

## 12. Skills, the Skill Registry & Commands (Source B Part III.3 ∪ Source A doc 02)

### 12.1 What a skill is (union)
Source B: a versioned, hermetic package in the Skill Registry containing five mandatory components: 1. **`SKILL.md` Manifest & Trigger Contract** (exact semantic triggers, required inputs, preconditions, step-by-step reasoning instructions, negative constraints — "what never to do" — and expected output artifacts) 2. **Bundled Deterministic Scripts & Toolchains** (pre-written Python, Rust, TypeScript, or Bash executing complex AST transformations, scaffolding, API handshakes, or verification checks deterministically without wasting LLM tokens) 3. **Reference Architecture & Golden Templates** 4. **Automated Skill Verification Harness** (dedicated micro-VM test suite proving the skill works before registry admission) 5. **Telemetry & Versioning Metadata** (success rate, average token cost, execution time, semantic version `v1.0.0`, instant rollback if an update degrades performance).
Source A distinctions layered: a **skill** packages a reusable procedure and its supporting resources; a **tool** performs an action; a **command** expresses user intent; an **agent** chooses and executes steps; a **workflow** controls state and transitions; a **model** supplies inference — keeping these distinct prevents a prompt from being mistaken for an implemented capability. Portable content baseline: the Agent Skills format — SKILL.md with name/description plus optional scripts, references, and assets (S01); operational metadata lives in the Alchemy registry alongside the package; optional fields are not assumed supported or enforced by every runtime. **The policy gateway enforces access independently: a SKILL.md cannot approve itself, expand a user's grant, disable verification, or override platform policy. A cryptographic signature identifies the publisher and protects integrity; it does not prove safe behavior.**

## 13. Autonomous Operations — operating envelopes, the loop union, healing, and the CSO function

### 13.1 The correct model for autonomy (Source A, doc 03 §§1–2)
Every loop follows one common contract: observe → establish context → diagnose or propose → check authority → act within scope → independently verify → observe outcomes → retain the learning. Diagnosis, containment, repair, and prevention are distinguished — restoring availability does not necessarily fix the underlying bug. Endless loops are not the default: every loop has a trigger, owner, state, deadline, attempt budget, cost ceiling, stop rule, and escalation destination. An improvement that increases cost or uncertainty without measurable benefit is not progress.

**Explicit operating envelopes (5 modes):** **Observe** (read authorized telemetry, inspect code, research, report — no external state change) · **Prepare** (reproduce, create branches, run isolated tests, draft repairs — no production effects) · **Bounded operate** (execute allowlisted runbooks and releases within standing grants — resource, time, cost, and impact limits enforced) · **Supervised change** (prepare consequential change with evidence and preview — concrete decision by authorized person) · **Restricted domain** (collect evidence and assist a qualified specialist — no claim of independent competence outside validated scope). Standing authorization is specific: actor, action class, resources, environment, maximum impact/spend, validity period, required evidence; it is checked at dispatch and immediately before consequential effects; revocation and stale evidence stop queued work too. Destructive data operations, changed permissions, new external commitments, uncontrolled spending, and changes to the control plane need stronger rules than a reversible UI fix; exact rules are configured with the owner, not invented by an agent during execution. Autonomy is earned per action class — there is no single global "fully autonomous" switch.

### 13.3 Healing state machine (Source A, doc 03 §4)
Detected → Investigating → (authorized containment) Contained → CandidateRepair → Verifying → (required checks pass) LimitedRollout → Observing → (recovery criteria met) Recovered; Verifying → Investigating on check failure; Observing → Rollback on regression; Rollback → Investigating when a known state is restored, → Escalated when state is uncertain; Investigating → Escalated on unknown impact or exhausted budget. Practice: gather deployment version, changes, metrics, traces, logs, queue depth, provider status, customer impact; redact secrets; reproduce in isolation where practical; compare competing hypotheses with the cheapest useful check; prefer a previously validated bounded recovery action to a novel production edit. Create the patch in an isolated branch; run the regression that would have caught the incident, integration/permission checks, and failure-path tests; stage a limited rollout where supported; use error rate, latency, data correctness, and real user success to decide promotion or rollback; observation duration depends on traffic and failure characteristics — a quiet minute is not enough evidence for a low-traffic system. Some effects cannot be rolled back (emails already sent, trades executed, records deleted without valid recovery points) and need reconciliation or compensating actions; database changes use compatibility-aware migrations — reverting application code can be unsafe if schema or data changed incompatibly. One repair owner per incident/component; fencing tokens reject stale workers. If external infrastructure is unavailable, degrade functionality truthfully, preserve queued intent safely, and avoid a retry storm. Diagnosis and successful recovery are measured separately (PROBE, S28).

## 14. Speed — how months or years compress into days honestly (Source B §12 ∪ Source A delivery rules)

1. **Start from Proven, Pre-Verified Ecosystem Foundations.** Hardened, production-ready foundational modules mounted into any new project on Day 1: authentication, passkeys, OAuth/SSO, and session security; multi-tenant workspaces and hierarchical organizations; granular RBAC/ABAC permissions; subscription, usage, and ledger billing engines; responsive executive and operational dashboards; multi-channel notification engines (email, SMS, push, in-app); immutable, tamper-evident audit logs; **the signature Interactive AI Activity Feed & Command Center**; resilient third-party integration and webhook harnesses; automated CI/CD deployment, OpenTelemetry monitoring, and backup pipelines.
2. **Parallelize Independent Work Across Locked Contracts.** Once schemas and API contracts (OpenAPI/Protobuf/GraphQL) are locked: visual design and frontend progress in parallel with backend API and database implementation; live documentation research for external integrations runs while core domain logic is built; independent QA agents author E2E and property-based tests against the contract while builders write the implementation; separate vertical features develop in isolated Git worktrees and ephemeral sandboxes so parallel agents never step on each other's files. (Source A adds: parallelize only genuinely independent work with defined contracts; coordinate shared schemas, files, identity, and APIs.)
3. **Build in Complete Vertical Slices.** Instead of 30 half-finished frontend screens with fake data, finish one high-value journey end to end before moving to the next: **Create Workspace → Ingest/Add Record → Verify External Data → Execute Domain Rule → Persist in Database → Record Audit Log → Render Live UI → Verify Persistence Across Refresh**. A working, testable product within hours; integration bottlenecks exposed immediately.
4. **Prove High-Uncertainty Items on Day 1.** Does the external provider actually offer the required API endpoint and payload fields? Can the customer's legacy data or firm portal be accessed reliably? Does the selected AI/ML or quantitative model achieve the required accuracy and latency on real samples? Can the expected transaction or media volume be processed at profitable unit economics? Are there legal, platform, or rate-limit restrictions on the planned automation?
5. **Reuse Validated Knowledge Without Copying Domain Mistakes.** Proven patterns from the Architecture Library are reused while re-validating domain fit — an eventual-consistency caching pattern suitable for a social media feed in Viral.ai or CampaignOS is unacceptable for real-time order execution and risk checks in Flex Algo or AlgoOS.
6. **Automate All Repetitive Verification Checks.** Compilers, type-checkers, linters, CVE scanners, multi-viewport visual captures, E2E browser journeys, and deployment smoke tests run automatically in the background on every change.
(Source A adds: no months-to-days promise is made without measured scope and dependencies, §15; and the first demonstration should include a failure, not only the happy path.)
